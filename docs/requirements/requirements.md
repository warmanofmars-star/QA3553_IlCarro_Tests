# Реконструированные требования IlCarro

Черновик v2 от 2026-11-05. v2: колонка «Факт» сверена с логом исследования, заявления
без подтверждения в логе помечены как *частично* или с указанием другого основания. SRS у проекта нет, поэтому требования восстановлены по источникам,
перечисленным ниже. Факты о поведении приложения — в `research-log.md` (ссылки вида `Q-API-01`).

## Как читать этот документ

**Источники**, по убыванию силы:

| Код | Источник | Где лежит |
|---|---|---|
| SW | Swagger (OpenAPI 3.0.1) | `docs/requirements/api-docs.json` |
| RFC | RFC 9110 HTTP Semantics | https://www.rfc-editor.org/rfc/rfc9110 |
| OWASP | OWASP API Security Top 10 (2023), ASVS 4.0.3 | https://owasp.org/API-Security/ |
| FE | Код фронтенда (бандл icarro-v1.netlify.app, имя файла указано) | сборка на 2026-11-05 |
| EXP | Исследование фактического поведения | `docs/requirements/research-log.md` |

**Правило применимости.** Код фронтенда (FE) — источник только для поведения интерфейса. Для API
действуют только SW, RFC и OWASP. Поэтому правило формы «цена ≥ 1» не делает ошибкой то, что API
принимает цену 0: это расхождение источников (раздел DISC), а не нарушение требования к API.

**Колонка «Факт»** — снимок на 2026-11-05 со ссылкой на вопрос исследования:

- *соблюдается* — поведение совпадает с требованием;
- *частично* — проверенная часть соблюдается, остальное не проверено (указано, что именно);
- *нарушается* — поведение противоречит требованию; кандидат в реестр известных багов;
- *не проверено* — исследование этот пункт не затрагивало, проверит тест;
- *не проверяемо* — проверку блокирует другое нарушение (указано, какое).

**Основание факта.** Ссылка `Q-…` — запись в `research-log.md`, воспроизводимая скриптом.
«Проба 2а» — ручной запрос при разборе источников, в лог не входит. «По коду» — вывод из кода
фронтенда, на экране не проверялся. Такие пункты в шаге 3 подтверждаются тестами.

**Три категории находок** (как в Phonebook):

1. Нарушение требования `REQ-…` или расхождение источников `DISC-…` → известный баг; в реестре
   ссылка на ID.
2. Наблюдение `OBS-…` → плохое поведение, для которого нет требования; источник ожидания назван явно.
3. Требование, которое соблюдается → обычный проходящий тест, защищающий хорошее поведение.

**Тег в тестах:** `@allure.tag("REQ-BOOK-01")`, `@allure.tag("DISC-02")`, `@allure.tag("OBS-04")`.

Имена файлов фронтенда содержат хеш сборки (`Register-CYJGzX27.js`) и меняются при новой выкладке.
Ниже они указаны без хеша: `Register`, `Login`, `LetCarWork`, `Search`, `CityAutocomplete`,
`CarDetails`, `Profile`, `cars` (вызовы API), `index` (авторизация, перехватчики, маршруты),
`default` (отображение цены).

## 3. Расхождения источников (DISC)

Источники противоречат друг другу. Расхождение — дефект системы или требований; в реестре багов
на него ссылаются по ID.

| ID | Суть | Источники | Последствие |
|---|---|---|---|
| DISC-01 | Правила пароля: фронтенд — не короче 6, буква и цифра; Swagger и API — не короче 8, заглавная, строчная, цифра, спецсимвол обязателен; текст ошибки API — спецсимвол «можно» (Can contain). | FE: `Register`; SW; EXP (Q-API-07) | Форма пропускает пароль, который API отклоняет; пользователь видит `"[object Object]"` (Q-UI-07) |
| DISC-02 | Города: во фронтенде 54, в API 37, общих 22. Разное написание: `Beersheba` / `Beer Sheva`, `Kiryat …` / `Qiryat …`, `Ra'anana` / `Raanana`. | FE: `CityAutocomplete`; EXP (Q-API-03) | Машину в 32 городах из подсказки добавить нельзя — «Failed to submit car» (Q-UI-03); поиск по ним молча пустой (Q-UI-12); 15 городов API из интерфейса недоступны |
| DISC-03 | Регистр email внутри API: регистрация приводит email к нижнему регистру (повтор с другим регистром — «User already exists»), вход — нет (email с заглавными — 401). | EXP (Q-API-06) | Через API пользователь не может войти тем же email, которым регистрировался. Интерфейс это скрывает, приводя email к нижнему регистру при входе (Q-UI-09) |
| DISC-04 | Поля формы машины Gear, WD, Doors (и `features` в состоянии формы) отсутствуют в `CarDto`; фронт их собирает и не отправляет. | FE: `LetCarWork`; SW: `CarDto` | Введённое пользователем молча теряется (Q-UI-05) |
| DISC-05 | Фронт обращается к эндпоинтам, которых нет ни в Swagger, ни на бэкенде: `GET /v1/cars/{id}`, `GET` и `PUT /v1/user/profile`. Страница машины читает поля, которых нет в `CarDto`: `make`, `car_class`, `image_url`, `engine`, `gear`, `wheels_drive`, `fuel_consumption`, `doors`, `address`, `distance_included`, `description`. | FE: `cars`, `CarDetails`, `Profile`; SW; EXP (Q-API-08) | Страница машины не работает (Q-UI-01). `GET /v1/cars/{id}` и `GET /v1/user/profile` отвечают 403 (Q-API-08), в браузере запрос машины завершается `net::ERR_FAILED` (Q-UI-01). `PUT /v1/user/profile` не проверялся |
| DISC-06 | Бронирование: Swagger описывает эндпоинт, фронт считает его не реализованным («Бронирование пока не реализовано в API»), API отвечает успехом, ничего не сохраняя. | SW; FE: `CarDetails`; EXP (Q-API-01) | См. REQ-BOOK-01, REQ-BOOK-02 |
| DISC-07 | Границы полей машины: фронт требует Seats ≥ 1 и Price ≥ 1; в Swagger ограничений нет; API принимает 0 и отрицательные значения. | FE: `LetCarWork`; SW; EXP (Q-API-05) | По правилу применимости это не баг API; поведение API — OBS-03 |
| DISC-08 | Пагинация: фронт передаёт `page` и `size` в поиск; в Swagger параметров нет; API их игнорирует. | FE: `cars`; SW; EXP (Q-API-02) | Пагинация работает только на клиенте; ответ не ограничен — REQ-SEC-07 |

## 5. Ограничения среды

- **Пользователей нельзя удалить:** в API нет такого эндпоинта. Каждый прогон тестов оставляет
  временных пользователей.
- **Бэкенд общий:** машины добавляют и удаляют другие пользователи. Абсолютные числа (например,
  число машин в городе) в тестах использовать нельзя.
- **Ответ поиска по крупным городам весит десятки мегабайт** (Tel Aviv — около 18 МБ). Для тестов
  поиска лучше брать города с малым числом машин.
- **Хеши файлов фронтенда меняются при новой сборке.** Ссылки на код фронтенда актуальны
  на 2026-11-05.
