# Требования к IlCarro

У IlCarro нет SRS и STD. Эта папка — источник ожидаемых результатов для тестов. Файлы здесь
хранятся в git: это наша работа, а не материал курса (в отличие от Phonebook).

## Содержимое

| Файл | Что это |
|------|---------|
| `api-docs.json` | Swagger (OpenAPI 3.0.1) бэкенда IlCarro, `info.version` = `v1.0.0` |
| `requirements.md` | Реконструированные требования: у каждого есть ID, источник и колонка «Факт» (снимок поведения на дату проверки) |
| `research-log.md` | Лог исследования: что отправили и что получили, без оценок. Вопросы `Q-API-NN` и `Q-UI-NN`; на них ссылается колонка «Факт» |

Лог создают скрипты из `research/` (запуск описан в `research/README.md`). Требования выводятся
из источников ниже, оценки делаются в `requirements.md`, а не в логе.

## Категории находок и теги в тестах

Каждая находка в `requirements.md` получает ID одной из трёх категорий:

| Категория | Что это | Что делает тест |
|-----------|---------|-----------------|
| `REQ-…` | Требование из источника (Swagger, RFC, OWASP, код фронтенда). Нарушение — кандидат в известный баг | проверяет требование |
| `DISC-…` | Расхождение между источниками (например, фронтенд и Swagger) | ссылается на расхождение |
| `OBS-…` | Наблюдение: плохое поведение, для которого требования нет; источник ожидания указан явно | фиксирует наблюдение |

Тест помечается тегом с ID из `requirements.md`:

```python
@allure.tag("REQ-BOOK-01")
def test_booking_is_saved(...): ...
```

Если подходящего ID нет, ID не придумывают: сначала его добавляют в `requirements.md` (решает пользователь).

## Иерархия источников ожидаемых результатов

От сильного к слабому. При конфликте побеждает источник выше.

1. **Swagger** (`api-docs.json`) — контракт API: пути, методы, схемы, коды ответов.
2. **HTTP RFC и OWASP** — общие правила протокола и безопасности (коды статусов, идемпотентность,
   проверка прав доступа, отсутствие утечек в ошибках).
3. **Код фронтенда** — бандл на https://icarro-v1.netlify.app: правила валидации форм, тексты
   сообщений, поведение UI.
4. **Исследование фактического поведения** — самый слабый источник. Поведение приложения само по себе
   не доказывает, что оно правильное: его можно использовать как гипотезу, но не как эталон.

Если ни один источник не задаёт поведение, тест его не утверждает, а вопрос выносится пользователю.
